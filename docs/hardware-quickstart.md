# Moonfall 联调启动说明

仓库：<https://github.com/TeresaPeng-zju/lunar-evacuation-race>

分支：`codex/hardware-sandbox`

环境：Node.js 20 或更高版本，支持 WebGL 的桌面浏览器。运行联调不需要 Blender、Unity 或额外构建。

## 1. 首次下载与启动

```sh
git clone --depth 1 --branch codex/hardware-sandbox https://github.com/TeresaPeng-zju/lunar-evacuation-race.git
cd lunar-evacuation-race
npm ci
npm start
```

以后在仓库目录执行 `npm start` 即可。服务默认使用内置无电机模拟器。更新前停止服务，在无本地代码改动的情况下执行 `git pull --ff-only` 和 `npm ci`，再启动。

| 屏幕 | 地址 | 内容 |
| --- | --- | --- |
| 电脑屏 | <http://127.0.0.1:4174/sandbox.html> | 完整 3D 基地、比赛状态、选路、落石和工作人员控制 |
| 27 寸行驶屏 | <http://127.0.0.1:4174/floor.html> | 实体机器人实际行驶的月面主赛区，三段背景与动态道路按各车进度切换 |

电脑显示设置选择“扩展显示”。先打开电脑控制台，点击“打开行驶屏”，将新窗口拖到 27 寸屏，再点击“全屏赛区”。行驶屏含完整月面、设施、信标、舱门、月震和终点；网格及车体包络仅在“坐标检查”时显示。

电脑端点击“配置地图”，等待定位与地图确认；双方选开局路线，再点击“双车发车”。模拟器可选 4× / 8× 加速及固定余震结果，便于验证完整一局。比赛结束后可重置下一局。

只保留一个主控窗口；额外控制台只读。关闭或刷新主控会使运行中的比赛暂停，恢复须按控制台的状态核对流程操作。行驶屏只订阅状态，不发送控制命令。`index.html` 是独立虚拟试玩，硬件联调使用上表入口。

## 2. 通过 WebSocket 联调，不连接电机

先用 `Ctrl+C` 停止前面的服务。终端一：

```sh
npm run hardware
```

终端二，在同一仓库目录运行参考硬件客户端：

```sh
npm run mock
```

浏览器入口不变。这时定位和执行回执通过真实 WebSocket 往返；mock 不驱动电机。先验证握手、配置地图、发车、落石绕行、换段、月震选路、终点停车和暂停恢复，再接入实际硬件程序。

## 3. 接入真实相机与小车

1. 停止 mock 和原服务。每次只允许一个硬件适配器连接，由它汇总两辆车。
2. 复制 `config/hardware.example.json` 为 `config/hardware.local.json`，填写实测标定与控制参数。本机配置不提交到 Git。
3. 在仓库目录启动：

```sh
npm run hardware -- --profile config/hardware.local.json
```

4. 硬件适配器连接 `ws://127.0.0.1:4174/hardware`，按 [完整协议](hardware-integration.md) 完成 `hardware.hello`、时钟同步、地图及路线回执，持续上传车体中心位姿。游戏端给出路线，硬件端负责沿路线行驶、原地回转、制动和本地失联停车。

协议版本为 `lunar-hw/0.3-sandbox`；地图版本为 `physical-v0.3-sandbox.1`。坐标单位 cm，左上角为原点，X 向右、Y 向下；朝右为 0°，顺时针为正。

当前地图约束为有效屏面 59.8 × 33.6 cm、车体 6 × 6 cm、可原地回转、最高速度 2 cm/s。实车发车还会校验标定编号、综合误差、制动距离、定位时效和并列判定窗口。模板中的空值必须通过实测填写，不能直接将 `parameters_verified` 改成 `true`。全屏后的有效显示矩形必须与相机标定一致。

服务只监听本机 `127.0.0.1`，适用于 USB 相机和硬件适配器运行在展示电脑上的方案。其他电脑不能直接用此地址连接；跨电脑通信需单独配置网络方案。

## 4. 排查与交接

| 情况 | 操作 |
| --- | --- |
| 端口已被占用 | 检查已有服务，或用 `npm start -- --port 4175`；外部模式用 `npm run hardware -- --port 4175`，实车时同时保留 `--profile` 参数。浏览器和适配器均改用相同端口 |
| mock 使用其他端口 | `npm run mock -- ws://127.0.0.1:4175/hardware` |
| 想检查实际厘米位置 | 电脑端展开“厘米坐标与车体包络检查”；行驶屏点击“坐标检查”，或打开 `floor.html?debug=1` |
| 操作按钮只读 | 检查是否已有主控窗口，不要另开一套服务来恢复同一场比赛 |
| 页面显示失联 | 检查 Node 服务、WebSocket 和硬件连接；先核对状态，再恢复比赛 |
| 导出正式路径 | <http://127.0.0.1:4174/api/map>；硬件按此配置及路线消息执行，不通过识别背景颜色寻路 |
| 导出排查记录 | <http://127.0.0.1:4174/api/trace>；同时记录复现步骤、比赛阶段及硬件日志 |
| 运行软件回归 | `npm test` |

已提供软件模拟及接口测试；工业相机标定、AprilTag 定位、实车路径跟踪、卡牌识别和本地保护仍由硬件端接入并现场验收。GitHub Pages 仅能展示静态页面，不提供联调服务。

完整字段、消息顺序和异常处理见 [硬件联调接入说明](hardware-integration.md)；双屏换段与坐标映射见 [双屏运行说明](dual-screen.md)。

## 手机 NFC 与单车运动联调

游戏服务随 `npm start` 或 `npm run hardware` 启动 NFC 接收，默认端口为游戏端口加 2。手机和电脑连同一局域网，打开控制台的刷卡器连接页查看地址。手机读取实体牌编号；接收服务将其映射到蓝黄玩家及牌型，提交给游戏状态机。

控制台的「实车定位与运动控制」提供现有独立工具的入口。在控制电脑上运行：

```sh
npm run rover
# 另开终端，使用已安装 cv2.aruco 和 numpy 的 Python 环境
CAMERA_PYTHON=/path/to/python npm run camera
```

遥控服务使用本机 4183 端口，相机页使用 4182 端口。原生采集使用 macOS AVFoundation、ffmpeg 和 icspring USB 相机。复用既有调试服务时可直接打开入口。相机页沿用同一浏览器来源的标定数据；新电脑或标签更换后需重新标定车头。A→B 直线控件使用四码场地毫米坐标；页面另显示游戏棋盘厘米坐标。当前自动定位控制只针对现场唯一的蓝车 ID 0。赛事发车仍由模拟器或连接到 `/hardware` 的比赛适配器执行，独立运动测试由操作员在相机页启动。

### 外部模拟与相机联调

1. 在单独端口运行 `npm run hardware -- --port 4204`，再运行 `npm run mock -- ws://127.0.0.1:4204/hardware`。打开电脑控制台，按“配置地图 → 选择开局 → 双车发车”操作。这里走外部 WebSocket，适配器接收整段路点，回传准备、锁定、生效回执和两台模拟车的带时间戳位姿。终点判定由游戏完成。
2. 做静态实车定位联调时，另开外部模式端口或先关闭 mock。打开仓库版本的相机页，完成棋盘、标签朝向及码到车体中心的偏移标定。在相机页「游戏路线与实测定位」连接对应的游戏端口，然后在控制台配置地图、选择开局路线。相机画面叠加两条游戏路线，控制台显示接收的车体中心（cm）和车头朝向（°）。缺失标签或偏移数据时对应车显示定位无效，超过 150 ms 的读数会失效。蓝车用 ID 0；黄车用 ID 1，需填写其自身偏角和前、右偏移。
3. 相机以无电机观测模式握手。它接收 `map.configure`、`match.configure` 和 `route.preview`，回传 `pose.frame`；不会把路线预览确认为运动指令。正式双车执行的准备、激活、回转和停车回执需由实车执行器提供。完整比赛和相机联调共用坐标、时钟同步、会话及硬件连接槽。

### 双车执行器：游戏发车、分车跟踪、换段和停车

`npm run executor` 是比赛执行器。每车独立保存段实例和路线版本，从反馈位姿计算轮速。游戏点击“双车发车”后两车使用同一个发车时刻。各车抵达段末、停稳后上报 TURNING，按各自目标转向，确认角度和静止后上报 READY；收到游戏的 route.activate 才进入下一段。末段回报 PARKED 之前必须收到终点位姿和停稳反馈。小车失联、定位超时或偏离批准路线会停止两车。游戏继续按实际入区帧判胜。

**不接车联调**：分别运行 `npm run hardware -- --port 4220` 和 `npm run executor -- ws://127.0.0.1:4220/hardware`。打开 http://127.0.0.1:4220/ ，配置地图、选路、双车发车。这个模式使用独立差速模型产生位置和朝向；模型只接收速度指令，不读取目标路线。模拟后端不创建电机 UDP 套接字。

**实车接线**：运行仓库版相机服务；执行器独占两车的 UDP 控制，手动遥控及相机页独立行驶测试应结束。相机页“连接游戏”和外部 mock 均要断开以释放硬件接口槽。把 `config/dual-executor.example.json` 复制到 `config/dual-executor.local.json`，核对两台固件 IP、标签、左右轮符号和校准数据；此文件已在 Git 忽略范围内。
四个锚点按左上 ID 4、右上 5、右下 7、左下 6 摆放。`origin_x_mm/y_mm` 是游戏左上角相对 ID 4 的场地坐标，示例对应居中摆放。每辆车的 `heading_offset_deg` 与相机页“车头朝右”标定的加性偏角相同；`forward_mm/right_mm` 从标签中心量到车体中心；`track_cm` 为轮距；左右 `pct_per_cm_s` 分别为单位轮线速度对应的有符号功率百分数，`max_power` 为实测上限。实测完成后填写唯一 calibration_id 及现有协议的误差、制动和平局窗口参数，再标记已验证。

两个进程使用同一份实测配置：
```sh
npm run hardware -- --profile config/dual-executor.local.json
npm run executor -- --live config/dual-executor.local.json ws://127.0.0.1:4174/hardware
```
执行器读取本机 4182 的相机帧，分别向车辆发送 UDP 8888 的 `左百分比,右百分比`，并轮询各车 HTTP `/status`。停稳需同时满足车端 L/R 为零和相机静止观测。现场还需核对固件自己的失联停车、两车转向、速度映射、相机覆盖及定位精度；模拟结果不等同实车验收。
